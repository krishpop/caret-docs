System and request flow ​

Caret separates routing, conversation execution and Mac I/O. The supervisor chooses the execution surface; the Pi worker handles a bounded foreground task; the native helper performs individual Mac operations.

Follow one foreground task ​

  1. The server receives a request and establishes trace/lifecycle state. The supervisor receives the user's request and chooses a tool.
  2. Under CARET_CU=v2, run_mac_task arguments are converted to a TaskSpec; the request trace ID is injected. The task needs a complete goal because its Pi conversation starts with only its task card and applicable context.
  3. The async adapter starts a task and returns its ID. task_status polls progress and eventually a structured result. A tool submission is not a completion claim.
  4. The runner creates or reuses a Pi conversation and stores caret.task. The model sees the mac-control extension and uses observe, act, and finish.
  5. act validates its action batch, applies guards and executor logic, checks observable predicates, and persists progress. The helper performs the Mac I/O.
  6. finish evaluates declared success checks and settles the task. The runner gathers usage, writes eligible task records, cleans secret state and returns the result.

The legacy mode instead uses a long-lived root conversation and seven simpler tools. The code selects legacy unless CARET_CU is exactly v2; the documented local setup uses v2. A reader should verify configuration rather than assume all installations use the same mode.
