Execution and safety ​

The model proposes a batch; the executor decides how to run it, checks the result, and returns evidence. Native helper guards remain a separate boundary because the Mac can change outside the agent's conversation.

The shared action schema rejects unknown properties, including inside targets and predicates. validateExecution validates the entire batch before snapshots, recorder reads, journaling or mutations. For example, press means accessibility activation and cannot also contain key or modifiers; keyboard input uses the key variant.

Targets and observations ​

observe defaults to the frontmost window. It can inspect window, app, menu bar or system scope and can attach screenshots. Per-task element IDs such as e14 come from /ax/snapshot; a role/name locator can address something that appears during a batch. Point coordinates are fractions of screenshot width and height from the top-left.

These IDs differ from the semantic keys and AX paths returned by recording's /ax/state. Never use a schema-lite element key as though it were a current Pi element ID.

For window/app observations with fewer than five nodes, observe automatically requests a screenshot. Larger trees containing mostly unnamed web groups require an explicit screenshot: true; the separate sparseTree heuristic helps the executor interpret changes but does not trigger automatic observation screenshots. Screenshots consume the image budget and are disabled in secret tasks. Seeing a screenshot is not a machine-verified success predicate.

Batch execution and replay ​

The model-facing tool permits one to five actions. Execution stops at the first failure, then evaluates expect with bounded polling. A diff or full observation comes back so the model can select the next approach. wait and verify check state without producing schema-lite action steps.

The executor journals actions around the helper call. Finished actions are skipped during replay. If a non-idempotent action was in progress at interruption, the executor cannot assume whether the physical effect occurred: it returns an uncertain/interrupted outcome rather than blindly repeating it. Helper idempotency keys add another layer; neither is a transaction over the entire desktop.

expect describes the resulting UI, not intent. After a send, the composer often clears: check the resulting conversation or page. The sendHint logic warns when a successful send/submit action is followed by a failed expectation, so a verification failure does not prompt a duplicate send.

Budgets and failure handling ​

Defaults are 20 batches, 60 actions, 300 seconds, 10 images and 3 failed approaches. The task type supports overrides; the supervisor-facing schema advertises only step and time overrides. Enforcement is at tool boundaries rather than a guarantee that an in-flight operation is interrupted at the precise budget deadline. The first act has a special budget-check exemption; image checks occur separately.

Repeated failed action fingerprints are rejected after two failed batches. Switching away from a failed approach contributes to the failed-approach limit. The task document records these decisions so progress and final results share a domain state.

Input policy is layered ​

The helper guards stop-latched or locked-screen actions and applications on the local input block list. The v2 executor also binds input to the expected app and checks active work, uncertain input context and existing user drafts. User-authorized drafting and sending remain separate decisions. ACTIVE_WORK, INPUT_CONTEXT_UNKNOWN, USER_DRAFT and GUARDED_WINDOW must not be bypassed through another input route.

The classifier and allow-list support action risk decisions, but a constraints.allow entry does not override hard blocks or uncertain destinations. Shadow approval logs are evidence, not a universal enforcement layer. The legacy harness installs its approval extension separately; v2 classifies its batches in the executor.

Secret handoff has additional local helper state and cleanup. It suppresses screenshots and step records and masks secret-shaped text. This is bounded secret handling, not general encrypted sensitive-document storage.
