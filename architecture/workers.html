Workers and delegation ​

A “worker” is a useful architectural term for something the supervisor delegates to. This checkout does not define one universal Worker interface or a plugin manifest that describes every worker. It has several concrete adapters with different contracts.

The Letta supervisor registers tools with a name, description, parameter schema and execution callback. Registration is the integration point. It does not turn all backends into Pi conversations.

Defining a Pi task ​

A Pi worker has four parts:

  1. Task card: the goal, observable success checks, constraints, app hints, optional plan, budgets and secret mode in TaskSpec.
  2. Agent configuration: model and reasoning effort on a newly created Pi conversation.
  3. Capabilities and instructions: the mac-control extension provides tools and a dynamic prompt section. Both modes register the same extension name so existing conversations can use the installed implementation.
  4. Domain state: caret.task stores the original spec, counters, plan, evidence and terminal result; caret.tasks maps trace IDs to conversation IDs.

An illustrative internal specification (this code block does not run anything):

ts
const spec = {
  trace_id: 'example-local-review',
  goal: 'Open TextEdit and create an empty document. Do not type or send.',
  success_criteria: ['TextEdit has an Untitled document window'],
  success_checks: [
    { window: { app: 'TextEdit', title: { contains: 'Untitled' } } }
  ],
  constraints: { forbid: ['typing', 'sending'] },
  budget: { max_steps: 4, max_seconds: 30 },
  plan: ['Open TextEdit', 'Create and verify the document']
};

Plain-language forbid text is task context; it is not a general sandbox policy. Enforced action rules live in the executor and helper. The supervisor-facing tool exposes a narrower shape than the full internal type: for example its budget schema advertises max_steps and max_seconds, and its plan items are strings. herdr is a different kind of worker ​

The supervisor steers agents already running in herdr with agent_list, agent_prompt, agent_wait, and agent_read. State detection and terminal output are part of that backend's contract. A background mode label does not mean those agents cannot affect files or external systems.

resume_in_herdr plans migration of supported sessions before the confirmed execution step. It preserves active-writer locks. Owned shell work uses Caret's own workspace and one tab per named shell; completion is detected with an exit-code marker, and long-running work is followed with shell_read.

Extending a backend today ​

Start at the existing tool factory for the relevant backend. Define precise input and output schemas, lifecycle and error behavior, and register it with the supervisor. Keep request ownership, cancellation and evidence explicit. Add fake-service coverage around the adapter. Do not assume the Mac helper's guard automatically constrains a shell or browser integration.

A general plugin package/capability registry and provider-neutral app-building worker interface are proposals in the project tracker, not implemented contracts in this baseline.
